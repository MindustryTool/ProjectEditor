## Context

The ModHjsonPanel currently parses `mod.hjson` into a form, then on every change regenerates the entire file from scratch via `toHjson()`. The `update()` function in `useFileContent` already debounces writes to disk, but the content passed to it is always a full rebuild — all 7+ lines reconstructed even when only one field changed. The panel stores no reference to the original raw content; it re-serializes from the form state every time.

## Goals / Non-Goals

**Goals:**
- Only the changed line(s) should be modified in the file content passed to `update()`
- When a single field changes (e.g., `name`), only the `name:` line in the stored content should be replaced
- When dependencies are added/removed, only the `dependencies:` line should be replaced
- The form should still validate all fields and derive initial values from the file

**Non-Goals:**
- Changing the `useFileContent` or `update` API — the signature stays `update(content: string)`
- Handling arbitrary HJSON outside the known fields — the parser is unchanged
- Rich diff or merge logic — only single-line replacement for known keys

## Decisions

1. **Store raw lines as a ref** — Keep `useRef<string[]>` initialized from the initial file data. On each field change, locate the line index for that field's key (e.g., `"name:"`) and replace that line. Join the lines back into a string and pass to `update()`.

   *Alternative considered: Keep the full content string and do regex replacement.*
   *Rejected because: Regex on the full string is fragile with multiline values (description) and harder to make correct for edge cases like empty values.*

2. **Track which field changed via a helper** — Create a `replaceLine(lines: string[], key: string, value: string): string[]` function that finds the line starting with `key:` and replaces it. For `dependencies`, reconstruct the full `dependencies: [...]` line. For `hidden`, use the boolean string.

3. **Initialize lines on first parse** — The existing `useEffect` that parses `data` into the form will also populate the lines ref. When `data` is an empty string, use the default HJSON lines.

4. **Full rebuild as fallback** — Keep `toHjson()` as a fallback for add/remove operations (but convert the result into a line replacement for the affected key). Actually, since add/remove only affects `dependencies`, we can just replace the `dependencies:` line.

## Risks / Trade-offs

- **Risk: Line order changes** → The approach assumes fields appear in a fixed order matching the `toHjson` output. Since the file is always written by this same editor, this is safe. If an external tool reorders lines, the first load will re-parse correctly, but subsequent line-by-line updates may target the wrong line index. **Mitigation**: Re-scan for the key prefix on each update rather than relying on a cached index.
- **Risk: Leading whitespace** → Only `trimStart()` is used by `toHjson()`, so values never contain leading newlines or meaningful indentation. Line targeting by `startsWith(key + ":")` is safe.
- **Risk: Dependencies line format** → The `[item1,item2]` format is generated by the editor. Line replacement will use the same format, so round-tripping is consistent.
